# Enhancement plan: Frappe MCP Bridge and AI Chat

**Status:** draft for review · **Written:** 2026-10-19 · **Baseline:** `feature/ai-chat` at `c8a2af8`
(MCP bridge, AI Chat, artifacts)

This is a menu, not a commitment. Mark each item **Keep**, **Drop** or **Later** in the review column,
answer the open questions at the end, and we will turn the kept items into phased build plans like
the artifacts plan.

**Effort:** S = up to a day · M = 2 to 4 days · L = 1 to 2 weeks. These are estimates for one developer
working with Claude, including tests on v15 and v16.

**Rules every item keeps:** strict permissions (nothing appears without the role), company data only
reaches models allowed to read it, changes wait for approval, everything is logged and billed, only
the Administrator deletes chats, and nothing generated by a model runs in Desk.

## 1. Gaps in what is built

Things noticed while building and testing that are not finished yet.

**G1. Live test the other providers.** Only DeepSeek has been tested against a real API. The Claude
adapter (prompt caching, thinking replay, refusals) and the OpenAI and Gemini paths were tested only
against fakes. Run the live script against each provider we will actually use, and keep it as a
manual check in the repo (keys read from the site, never stored in files).
*Needs:* a test key per provider.

**G2. Prove live streaming in a real deployment.** Locally, socket.io refuses the `127.0.0.1` namespace,
so only the polling fallback was seen working. Check on staging that text streams word by word and
that the "Thinking…" state clears without polling.

**G3. DeepSeek's thinking output.** The OpenAI-compatible adapter ignores `reasoning_content`. Check
DeepSeek's current rules for thinking mode with tool calls (whether the reasoning must be sent back
within the same turn) and replay it if required. Then bill and show reasoning tokens as we do for
Claude.

**G4. Scrub secrets from attachments and form context.** Typed messages are scrubbed; attachments and
the opened document are not (the README says so). Run the same scrubber over extracted PDF and CSV
text and over form context, and tell the user what was removed.
*Watch:* never alter the user's stored file; scrub only what is sent.

**G5. Hide the workspace when AI Chat is off.** The page and button respect the switch, but the
AI Assistant workspace stays visible.

**G6. Empty chats.** A chat can be created and never used (for example, a file uploaded and the tab
closed). Add a daily job that removes chats with no messages after a day. Those chats hold no
messages, so the Administrator-only deletion rule isn't affected, but confirm that in review.

**G7. Long chats.** Opening a chat loads every message, and a full refresh reloads them all. Load the
latest page and fetch older messages on scroll.

**G8. Browser tests in CI.** The end-to-end checks (fake OpenAI-compatible server, approval cards,
hostile HTML, SVG and chart labels that must stay inert, no outside requests) were run by hand. Move
the fake server and those checks into the repo and run them with Playwright in the existing CI
matrix (v15 and v16). This also gives the JavaScript sanitisers (`format.js`, `artifacts.js`)
automated coverage, which they have none of today.

**G9. Print HTML artifacts.** Pages run in a sandbox the panel can't print, so users download and
print. Option: render a PDF on the server with networking switched off in the renderer. Only worth
it if users ask for it.

**G10. README address.** The README says `/app/ai-chat`; on v16 the page lives at `/desk/ai-chat`.

## 2. AI Chat: more useful day to day

**E1. Ask AI on list views and reports.** Send the selected rows, or the report's current filters and
results, with the first message. Same rules as Ask AI on forms: read with the user's permissions,
masked, size-capped, and only to models that may read ERP data.

**E2. Draft emails and replies.** A "Draft with AI" button in Frappe's email composer, seeded with the
thread and the linked document. It fills the composer and never sends; the user edits and sends.

**E3. Scheduled prompts.** "Every Monday at 8:00, summarise last week's sales and email me." Runs as the
user, inside their budget, with read-only tools only, and saves the result as a chat plus an email.
*Watch:* unattended runs must never propose changes; pause the schedule when the user loses the role
or the budget runs out.

**E4. Row-by-row approval for bulk changes.** `bulk_update_documents` and `import_records` are already
in chat behind one approval card. Add a per-row preview with accept or reject for each row, so a user
can approve 18 of 20 price changes.

**E5. Search over company documents.** A read tool that searches Files (PDF and text), Help Articles
and Wiki pages the user may read, so answers can quote company policy or a contract. Start with
keyword search; consider embeddings only if keyword search proves weak.
*Watch:* file permissions; private files must stay private to their owners.

**E6. Feedback on replies.** Thumbs up or down with an optional note on each reply, and a manager
report by model and template. It tells us which models and templates are worth paying for.

**E7. Regenerate or retry with another model.** History is append-only and frozen for preserved
thinking, so regenerating adds a new reply and marks the old one excluded (the same flag the
fallback model already uses). Retrying with a model that may not read company data stays blocked
once the chat holds company data.

**E8. Arabic and right-to-left.** The app has no translations yet. Add Arabic translations for every
user-facing string and check the chat, panel and drawer in RTL. Model replies already follow the
user's language.

**E9. Search inside messages.** Sidebar search matches titles only. Add search over message text, the
user's own chats only (managers in the audit view).

## 3. Artifacts: next steps

**A1. Refreshable artifacts.** Today an artifact is a snapshot. Store the read-only tool calls that
produced its data; **Refresh** re-runs them as the person viewing it, with their own permissions, and
saves a new version. A colleague with less access sees less, never more.

**A2. Chart artifact to Dashboard Chart.** When a chart came from one report, offer to create a real
Frappe Dashboard Chart on that report, so it lives on a workspace and stays current. Charts built
from free-form data can't be converted.
*Watch:* never use Custom HTML Blocks for this; they run HTML in Desk.

**A3. Export dashboards.** PNG and PDF for whole dashboards (charts and tables together), using the
same no-network rules as the chart PNG.

**A4. Share an artifact.** Read-only sharing with named colleagues. The hard part is data: the
artifact may contain figures the colleague can't see in the ERP. Options: allow sharing only for
artifacts made without ERP data, or for those made by A1 (which re-run as the viewer).
*Needs:* a decision on which option.

**A5. Mermaid diagrams.** Flowcharts and sequence diagrams from text. Render to SVG on the server, or in
the existing sandbox, never in Desk's own page, then show the result as an image like SVG artifacts.

**A6. Interactive artifacts.** Small apps with scripts (calculators, what-if sliders), off by default
behind an Administrator switch.
*Watch:* the main risk is that a script can navigate its own frame to an outside address carrying data,
and the sandbox has no way to block that. This needs its own security design before any build.

## 4. Governance, cost and compliance

**C1. Retention policy.** Archive chats after N days, and optionally delete after M days. Deletion must
stay with the Administrator account: the setting should be editable by the Administrator only, and the
job runs as the Administrator, keeping restorable copies in Deleted Documents.
*Needs:* your legal retention period.

**C2. Spend by department or cost center.** Tag usage with the user's department or cost center, show
it in the usage report, and optionally prepare a monthly journal entry or purchase invoice draft per
provider when ERPNext is installed (a draft only; finance submits it).

**C3. Mask personal data.** A per-model option to replace emails, phone numbers and ID numbers (such as
Qatar ID) in tool results and context with placeholders before sending, and to restore them in the
reply shown to the user.
*Watch:* masking can break answers that depend on the masked values; the user should see that masking
happened.

**C4. Price catalogue.** Prices are typed in by hand. Ship known prices per provider and model as
suggestions, keep a history of price changes, and warn when a provider's published price differs.

**C5. Per-minute rate limits.** Budgets and daily message limits exist; add a short-window limit per
user to stop runaway loops or scripted abuse.

**C6. Tamper-evident audit.** Chain a hash through each chat's messages so that a change made directly
in the database shows up, and add an auditor export (CSV or PDF) per chat or per user.

**C7. Provider health.** Latency, error and fallback rates by provider and model, from data AI Chat
Message already stores, as a manager report or dashboard chart.

## 5. MCP bridge

**M1. Prompt templates as MCP prompts.** The MCP endpoint answers `prompts/list` with an empty list.
Expose the AI Prompt Templates the user's roles allow, so Claude Code and the claude.ai connector get
the same ready-made prompts as the in-app chat.

**M2. Resources.** `resources/list` is empty too. Offer doctype schemas and the report list as MCP
resources, which clients can attach as context without spending tool calls.

**M3. Approve MCP writes in Desk.** Today MCP writes depend on write windows. Add an option where a
write from an MCP client becomes a pending action that a named approver accepts in Desk, reusing
AI Chat's approval cards.

**M4. Capability profiles per client.** Different capabilities for the claude.ai connector, Claude Code
and Codex (for example, read-only for the connector), chosen by the OAuth client or the API key.
